## Row 1 — confirmed, with the mechanism

REPORTED as: "I double-click the range in the QGIS symbology and edit
the numbers by hand... regardless of *how* I do it, changes to the Q
symbology are not reflected in the plugin." With two screenshots: QGIS
holding `0-10, 10-20, 20-30, 30-50, 50-80` on `Percent_White` while
the plugin's colour editor showed `3.1-18.3, 18.3-33.5, 33.5-48.7,
48.7-63.9, 63.9-79.1`.

THE COLOURS IN BOTH PANELS MATCHED (`#feebe2` through `#7a0177`),
which is the whole clue. Colours agree; only the numbers disagree.

MY FIRST DIAGNOSIS WAS WRONG AND THE CONTROL ARM CAUGHT IT. I read
`_graduated_layer_edited`, saw it decide adoption by comparing
`[r.symbol().color().name() for r in ranges]`, and concluded that
retyping a boundary moves no colour and so returns early. The probe's
control arm — the same edit with a colour ALSO changed — failed too,
which that diagnosis cannot explain.

THE ACTUAL MECHANISM is structural rather than a guard.
`_current_graduated_classes` never reads the layer's ranges at all. It
REBUILDS a renderer through `bridge.make_graduated_renderer` from the
plugin's own record: variable, ramp, scheme, k, outline, reverse,
range window, positional picks and `pinned`. A break retyped in QGIS
lives only in the layer's renderer, and there is no path by which it
enters `pinned` — so the editor, the swatch and the table cannot show
it whatever the layer holds. Colour has an adoption path; the BOUNDS
have none.

WHY THE EXISTING GUARD PASSES ANYWAY: the test that covers this route
pastes a renderer with a different FIELD, a different class COUNT and
a different RAMP, all of which the record does hold. The user's edit
changes none of those — same field, same count, same ramp, same
colours, two numbers moved — and that is the case nothing covers.

PROBE: `tools/probes/breaks_retyped_in_the_dock.py`, two arms
(BOUNDS_ONLY, CONTROL). Both report `AGREES WITH QGIS: False`.

## Row 2 — NOT A DEFECT, and both of my diagnoses were wrong

THE SOURCE DATA'S MINIMUM IS 3.1. The 9.7 came from the TILE layer's
attribute table. At that spacing the tiles miss some areas, so the
tiles' lowest value sits above the region's, and the tester reports
that widening the spacing until nothing is missed brings the two back
into sync.

So the plugin is doing what `_classification_values` documents: one
entry per AREA of the region, gaps included. Nothing is manufacturing
a minimum, no pin is stale, and the ladder 3.1 to 79.1 in steps of
15.2 is the correct equal-interval cut of the source column.

WHAT THIS COST, AND THE LESSON, which is the only reason to keep the
row. I had TWO diagnoses and both were wrong, the second in the more
dangerous way. The pin story -- a stale low pin of 3.1 stretched by
`_apply_pinned_bounds` -- accounted for EVERY measured number: the
exact top, the 6.6 at the bottom, the step that was not the span over
five. It was arithmetically perfect and false, because the PREMISE was
false: 9.7 was never the column's minimum. A hypothesis that explains
all the numbers is not thereby confirmed when one of those numbers is
a mismeasurement. Establish what a figure MEASURES before building on
how well it fits.

THE DESIGN QUESTION, which is the maintainer's and is left open. The
tester puts it plainly: "there could be a debate about which range of
values (source data or tiles) is the appropriate one for setting the
limits, BUT we have been talking about symbology derived from the tile
layer not the source." The plugin classifies from the SOURCE, which is
what keeps a classification stable when spacing changes; classifying
from the TILES would make the legend describe exactly what is drawn,
at the price of every break moving whenever the spacing moves. Both
are defensible and this is a decision, not a defect.

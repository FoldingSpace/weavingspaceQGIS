## Row 1 — confirmed, with the mechanism

REPORTED as: "I double-click the range in the QGIS symbology and edit
the numbers by hand... regardless of *how* I do it, changes to the Q
symbology are not reflected in the plugin." With two screenshots: QGIS
holding `0-10, 10-20, 20-30, 30-50, 50-80` on `Percent_White` while
the plugin's colour editor showed `3.1-18.3, 18.3-33.5, 33.5-48.7,
48.7-63.9, 63.9-79.1`.

THE COLOURS IN BOTH PANELS MATCHED (`#feebe2` through `#7a0177`),
which is the whole clue. Colours agree; only the numbers disagree.

MY FIRST DIAGNOSIS WAS WRONG AND THE CONTROL ARM CAUGHT IT. I read
`_graduated_layer_edited`, saw it decide adoption by comparing
`[r.symbol().color().name() for r in ranges]`, and concluded that
retyping a boundary moves no colour and so returns early. The probe's
control arm — the same edit with a colour ALSO changed — failed too,
which that diagnosis cannot explain.

THE ACTUAL MECHANISM is structural rather than a guard.
`_current_graduated_classes` never reads the layer's ranges at all. It
REBUILDS a renderer through `bridge.make_graduated_renderer` from the
plugin's own record: variable, ramp, scheme, k, outline, reverse,
range window, positional picks and `pinned`. A break retyped in QGIS
lives only in the layer's renderer, and there is no path by which it
enters `pinned` — so the editor, the swatch and the table cannot show
it whatever the layer holds. Colour has an adoption path; the BOUNDS
have none.

WHY THE EXISTING GUARD PASSES ANYWAY: the test that covers this route
pastes a renderer with a different FIELD, a different class COUNT and
a different RAMP, all of which the record does hold. The user's edit
changes none of those — same field, same count, same ramp, same
colours, two numbers moved — and that is the case nothing covers.

PROBE: `tools/probes/breaks_retyped_in_the_dock.py`, two arms
(BOUNDS_ONLY, CONTROL). Both report `AGREES WITH QGIS: False`.

## Row 2 — CONFIRMED, and my hypothesis was wrong

REPORTED as: "the minimum value on that Percent White variable in the
plugin symbology is NOT the minimum value in the data."

I GUESSED THAT THIS WAS ROW 1 IN DISGUISE — that the panel's `0.00`
was a number the tester had typed and the plugin's `3.1` was the
column's true minimum. THE ATTRIBUTE TABLE SAYS 9.7. The plugin is
showing a lowest bound BELOW ANYTHING IN THE DATA, which is a second
defect and not a view of the first.

THE ARITHMETIC IS NOT THE FAULT, which narrows it usefully. The
reported ladder is 3.1, 18.3, 33.5, 48.7, 63.9, 79.1: a step of
exactly 15.2, five equal intervals across 3.1 to 79.1. The equal
interval computation is doing its job on a wrong MINIMUM rather than
computing wrong breaks from a right one.

AND IT IS NOT ABOUT CLASSIFICATION AT ALL. Switching the element back
to Unclassed, which takes the column's range directly rather than
cutting it, still treats 3.1 as the minimum. So the fault is in what
the plugin believes the column CONTAINS, upstream of every scheme.

EXCLUDED 2026-08-18: it is NOT another column's minimum. The tester
checked. That kills the field-lookup story below, which was the
cheapest thing this could have been, and it also rules out the whole
family of "the plugin is reading the wrong column" explanations --
whatever 3.1 is, it was computed FROM Percent_White rather than found
in some neighbouring field.

WHAT THAT LEAVES. The value is derived, stable across schemes, and
below the data. So something is EXTENDING the column's range downward
rather than misreading it: a buffer, a trim, a fallback minimum, or a
set of values that includes entries the attribute table does not --
gaps materialised as numbers, or a No Data split feeding its own
sentinel back into the range. `_classification_values` promises "one
entry per area, GAPS INCLUDED", and what a gap becomes on the way into
that copy is now the first question, not which column it came from.

MEASURED 2026-08-18. The attribute table gives 9.7 and 79.1; the
plugin draws 3.1 to 79.1.

    end      data    plugin    out by
    top      79.1    79.1      NOTHING -- exact
    bottom    9.7     3.1      6.6

The top is not merely close, it is EXACT. So the maximum is read
correctly from the column and carried through untouched, and only the
minimum is manufactured.

ONLY THE MINIMUM IS WRONG. The top arrives intact, so nothing is
scaling, buffering or transforming the RANGE -- either of those moves
both ends. Something computes the minimum by itself and gets 3.1 where
the column holds 9.7. Whatever it is takes no notice of the maximum,
which is a strong constraint on the shapes that can produce it: a
symmetric buffer is out, a percentile over the same values is out
(it would move the top too unless it is one-sided), and any rescale is
out.

THE ARITHMETIC, which is where the next reader should start. The
plugin's span is exactly 76.0, cut into five steps of exactly 15.2.
The column's span is 69.4. Note what falls out of the exact maximum:
3.1 = 79.1 - 5 x 15.2, so the bottom is not an independently wrong
minimum at all -- it is the top MINUS five steps. The step is the
thing computed wrongly, and the minimum is merely where that step
lands when counted down from a correct maximum.

So the question is no longer "where does 3.1 come from" but "where
does 15.2 come from", and 15.2 is not 69.4/5 = 13.88. What set of
values, or what count, makes a step of 15.2 the right answer? 76.0 is
the span of something. Finding what has that span names the defect.

THE TESTER'S OWN HYPOTHESIS, 2026-08-18, and it fits the arithmetic
exactly: "something to do with how pin values are treated in the
translation between symbolisation schemes."

A PINNED LOW BOUND OF 3.1 PRODUCES THIS EXACTLY. `_apply_pinned_bounds`
stretches the outermost computed class out to the pin, so the ladder
runs from 3.1 rather than from the column's 9.7, the maximum is left
alone because nothing is pinned there, and equal intervals then cut
76.0 into five steps of 15.2. Every measured number falls out of it:
the exact top, the 6.6 at the bottom, the step that is not the span
over five.

It also explains why 3.1 is not any column's minimum. It was never
READ from data at all -- it is a number that was STORED, under some
earlier scheme or column, and honoured afterwards. That is what makes
this a pin-lifetime defect rather than a classification one, and it is
the same record row 1 writes into, which is why the two rows are
likely one fault seen from both sides.

THE DECISIVE TEST, cheap and worth doing before any code is read: open
the element's colour editor and look at the PIN column on the first
row. If it is pinned, unpin it and see whether the lowest bound
returns to 9.7. If it does, this is confirmed and the hunt is for what
set that pin and why a scheme change did not clear it. If the row is
NOT pinned while the ladder still starts at 3.1, then a pin is being
honoured that the editor does not show, which is a worse fault and a
different one.

SUPERSEDED, kept because it was wrong for a reason worth remembering: `_classification_values` builds a
separate geometry-less layer holding one entry per area, and the
renderer then resolves the field BY NAME in that copy. A lookup
landing on a different column would produce exactly this — a minimum
that is coherent, stable across schemes, and foreign to the column
being mapped. The question that would confirm it in one look is
whether 3.1 is the minimum of some OTHER numeric column in that
layer.

The probe's own fixture cannot settle this: `v1` spans 0 to 3 over
four distinct values, degenerate against five classes.

`_classification_values` reads the REGION layer, one entry per area
with gaps included, so "the plugin classified the tiles instead of the
areas" is already excluded as a cause.

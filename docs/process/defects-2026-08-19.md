## Row 1 — the tester's report, closed

A ladder retyped by hand in QGIS's Symbology panel kept its interior
breaks and lost its ends: 0 typed over a column starting at 3.1 came
back 3.1, and 80 typed over one ending at 79.1 came back 79.1. The
record had nowhere to put them, `low` and `high` naming the first
class's UPPER bound and the last class's LOWER. `pinned` gained
`floor` and `ceiling`.

MY OWN LEDGER ENTRY OF 2026-08-18 IS WHAT SHIPPED IT. It argued the
low end was harmless because the same areas fall in the same class,
which is true about colour and false about what the LEGEND says — and
it only ever considered the bottom.

## Row 2 — found by the matrix, and nothing to do with the feature

On a column of about 1e9, a ladder retyped to 0–80 had its ceiling of
80 adopted, which excluded every value, emptied the classification
pool, and left the element with NO CLASSES where it had drawn five.
The element's own layer went empty and the map lost it.

IT WAS ONLY REACHABLE THROUGH THE NEW MAGNITUDE AXIS. Both spine
shapes live between 0 and 80, where the same retype is perfectly
sensible, so no sample of them could ever have shown it. `huge` has
joined the spine permanently under the rule that a cell which has ever
failed is tested forever.

Adoption now keeps the interior breaks and drops the pair of edges
when nothing survives them, so the ends fall back to the column's own
extremes exactly as before the feature. Somebody typing a ladder that
misses their data has made a mistake rather than a request.

## Row 3 — tile-as-icon count check, OPEN

REPORTED as: "tile-as-icon number checking is wrong — it seems to
estimate based on doing a tiling and prevents you doing something that
should be fine if there's just one tile unit per map area."

REPRODUCED 2026-08-19, and the tester's own words were exact. The
three questions this row asked are all answered, the first by reading
and the rest by measurement.

DOES THE GUARD RUN AT ALL IN ICON MODE? It is the general estimator,
used unconditionally, in BOTH gates: `dialog.py`'s live-update gate
asks `estimate_tile_count_bounds` and its hard gate asks
`estimate_tile_count`, and `as_icons` is not read until fifty lines
below the second of them.

WHAT IT ESTIMATES. `estimate_tile_count_bounds` mirrors `_TileGrid` --
a circle enclosing the region's bounds, stepped by the unit's two
translation vectors -- so it scales with 1/spacing squared. Icon mode
is not that at all: `Tiling(unit, region, as_icons=True)` puts ONE
unit on each area, so the true count is areas times elements and the
spacing decides how BIG an icon is drawn rather than how many there
are. Measured on twenty-five areas with a four-element unit, by
`tools/probes/the_icon_count_is_a_tiling_estimate.py`:

    spacing 40   guard 103,914   drawn 100   asks "are you sure"
    spacing 28   guard 208,521   drawn 100   REFUSED OUTRIGHT

A factor of two thousand at the finer spacing, on a design that draws
a hundred tiles.

WHICH SENTENCE. The SIZE GUARD, not the inset collapse: "A spacing
this small asks for roughly 208,521 tiles. For this layer a spacing of
about ... or more will work." The advice is also wrong in icon mode,
where a larger spacing draws bigger icons and not fewer of them.

AND THE LIVE GATE FAILS QUIETLY IN THE SAME WAY, which nothing in the
report named: at either spacing the estimate is past
`LIVE_UPDATE_MAX_TILES`, so live update is paused with "about 103,914
tiles" for a map of a hundred. Somebody working in icon mode simply
finds the map stops following them.

## Row 4 — twenty-three elements is very slow, OPEN

REPORTED as: "a dataset displayed with 23 elements as little squares
for the tiling unit is extremely slow to work with due to having this
many elements."

NOT YET MEASURED, and it must be measured rather than guessed. This
project has one precedent that is probably the shape of it: the table
was rebuilt 461 times in a single test at 0.24.2 and 1,282 times at a
later HEAD, each rebuild redrawing a ramp swatch for every ramp in the
style library for every row — 306,558 draws in one test. With 23 rows
rather than 4, anything per-row-per-ramp multiplies by six.

THE TECHNIQUE THAT WORKED THEN, and should be used again: profile the
same interaction at two element counts and diff the CALL COUNTS, not
the seconds. Counts are immune to profiler overhead and to whatever
else is running; the self-time ratio understated a threefold
difference as 1.2x while the call counts carried it exactly.
`tools/probes/one_interaction.py` takes the tree to measure as an
argument, so two element counts can be compared directly.


## Row 23 — the guard refused a map the library draws

FOUND BY A PERFORMANCE QUESTION and answered as a refusal. The
maintainer asked how long their own upstream script takes against the
plugin's equivalent; the plugin never got as far as a time, because it
declined the design:

    A spacing this small asks for roughly 585,765 tiles. For this
    layer a spacing of about 17,500 map units or more will work.

The same design through the library draws 70,659 tiles in about five
seconds. An overshoot of 8.3x, and a user who simply cannot make their
map.

WHY: `estimate_tile_count_bounds` mirrored `_TileGrid`, covering a
CIRCLE enclosing the region's bounding rectangle. The library then
CLIPS to the polygons. New Zealand is two long islands in a rectangle
that is mostly sea -- 11.8% of that circle -- so seven tiles in eight
were counted and never made. A circle round a rectangle is pi/2 times
its area at best, worse when the rectangle is long, and over a sparse
region the two compound.

FOUR MODELS WERE MEASURED, against what the library really draws,
because a region is not one shape: adjacent cells cut from a raster
share edges that need no allowance, while separated cells each carry
their own.

    model                     adjacent cells   separated cells
    bounding-box edge              1.20x           0.98x  UNDER
    each polygon's perimeter       6.25x           2.38x
    DISSOLVED boundary             1.28x           1.68x

Only the dissolved boundary is generous on both, and a guard that
under-counts waves through a run that then takes the machine. The
bounding-box variant was written first and a guard caught it 2% under
within the hour, which is the guard earning its place before the
feature was even committed.

COST: dissolving 3,011 polygons takes about 0.05s, which the hard gate
can carry once per Generate. The LIVE gate still asks the bounds-only
form, which assumes the region fills its extent -- the most generous
thing a caller holding nothing but a layer extent can honestly assume.

AFTER: 91,685 estimated against 70,659 drawn, and all 23 element
layers made. The map the plugin refused this morning is the map it
draws now.

WHY NOTHING HERE CAUGHT IT: every region fixture in this suite is a
dense square, so the circle and the ground differ only by pi/2 and
any honest threshold accepts both. The new guard therefore asserts its
fixture is SPARSE before it compares anything, and computes what the
old arithmetic would have said so that the threshold cannot be one the
current code merely happens to meet.

## Row 4, closed: a regression this version introduced

MEASURED AGAINST THE REPORTER'S OWN DATA rather than a fixture --
`23-mosquitos.gpkg`, 3,011 polygons and 23 REAL columns -- because the
suite's four elements over thirty-six features is a factor of 481 away
with no change of shape, which is why nothing here could ever have
seen it.

    calls per interactive tick   v0.24.0 122,066   v0.24.2 119,352
                                 HEAD  1,041,176
    CPU per tick                 170.5 ms   172.1 ms   3,543.4 ms
    one Generate                 2.9 s      2.5 s      62.7 s

NOT A STANDING COST. `_classification_values` exists at neither tag,
so this arrived with 0.24.3. `_assignments` asks `_value_digest` for
every element, every digest routes through that function, and the
function REPLACED its cache dict on each miss -- sound reasoning about
staleness that also threw away every other column's entry. Twenty-three
elements on twenty-three columns is a zero hit rate, so one keystroke
rescanned 3,011 features twenty-three times and built twenty-three
memory layers.

THE COARSE SPACING IN THE REPORT WAS THE CLUE. Held at 169 tiles and
at 853 the four per-tick counts are identical to the digit: not
tiling, not rendering, nothing that scales with the map. A hex design
at 23 elements gives the same counts, so it is not grid-specific and
the anthromes report is very likely this same fault.

THE FIX keeps one entry per column and drops only what the fingerprint
or `_data_version` has moved under, which is the same condition the
lookup already tests -- so there is no window in which a stale entry is
reachable. Measured here after the fix: four elements on four columns
cost four scans cold and ZERO warm, against four every tick before.

THE GUARD HAD TO BE WRITTEN CAREFULLY, and the agent that measured
this said so before it was: a ONE-COLUMN test reads zero warm scans
whatever the code does, since there is nothing to evict it, so it
would pass with the cache deleted outright. The guard therefore counts
scans across SEVERAL columns and asserts the cold count first, since a
fixture that never fills the cache makes the warm count meaningless.

## Row 5 — a QGIS crash with no plugin in it

REPORTED as a full macOS crash report: QGIS 4.2.0 on macOS 26.5.2,
`EXC_BAD_ACCESS` reading address 0x8 on the main thread.

WHAT THE STACK SAYS, and it is worth reading before anything else is
assumed:

    QgsLayerTreeView::contextMenuEvent(QContextMenuEvent*)
      QMenu::exec(QPoint const&, QAction*)
        QMenuPrivate::popup(...)
          QWidgetPrivate::show_sys()
            QCocoaWindow::setVisible(bool)

NO PLUGIN FRAME APPEARS AT ALL -- no Python frames, no
`weavingspace_qgis`, nothing between QGIS's layer-tree view and Qt's
Cocoa window code. It is a null window being asked for its state while
a context menu is shown.

AND THE PLUGIN DOES NOT TOUCH THAT MENU. Checked rather than assumed:
nothing in the package references `contextMenu`, `layerTreeView` or
`addCustomActionForLayer`, so it contributes no action to the layer
tree's context menu and cannot be building the QMenu that crashed.

WHAT WOULD CHANGE THAT VERDICT, since "no frame" is evidence rather
than proof. A crash while SHOWING a menu can be provoked by state the
menu reads, and this plugin does put layers and a group into that
tree. The questions worth asking, in order:

* does it reproduce with the plugin uninstalled, on the same project;
* does it reproduce right-clicking a layer the plugin did NOT create;
* does it happen only after the plugin has removed or replaced a
  group, which is when a layer-tree node could be stale.

VERSION WORTH NOTING: 4.2.0. CI covers 4.0.0, 4.0.3 and `stable`,
which is 4.2.1 -- so this is a version nothing here tests, and the

## Row 6 — the adopted ladder moved the row and told nothing

A five-class ladder retyped in QGIS's Symbology panel is adopted into
`_pinned_bounds` as `breaks`, `floor` and `ceiling`. Those three are
carried in the row's signature. `_last_signatures` went on naming the
row as it read BEFORE the adoption, so the next run's landing compared
the two, found them different, called the element CHANGED and re-seeded
it -- over a twelve-class Classify the user had pressed in the dock
while that run was in flight.

THE LAYER ALREADY WEARS WHAT WAS ADOPTED, so "unchanged" is the honest
answer at the landing and the renderer is preserved. Four colour
adoption exits already record the signature for exactly this reason and
say so at the line; this one is the bounds' twin and was written
without it.

FOUND BY BISECTION RATHER THAN BY A FIFTH THEORY, which is the part
worth keeping. Four hypotheses had each been implemented and each been
wrong. Swapping `dialog.py` for its last-good copy settled the FILE in
one run; bisecting its eight revisions settled the COMMIT; a file-based
dump of the landing's own verdict then named the term:

    LAND b unchanged=False kept=False oldk=12 prev==sig False
      SIG-DIFF b term 14 () -> (('breaks', ...), ('ceiling', 4.0),
                                ('floor', 0.0))

The repaint that had masked it -- `_replay_deferred_adoptions` calling
`_apply_style_change` -- was gated on live update on 2026-08-19, which
is correct and stays: with live update off the map is not refreshed on
its own. What the gate exposed was that nothing else stopped the
landing clobbering the user's work. Fixed in the commit that carries
`an-adopted-ladder-moves-the-row-signature`.

## Rows 7, 8 and 9 — what eight hunts found in the new feature

Eight hunts were launched at the maintainer's asking on the ground
around the floors-and-ceilings work and the QGIS-edit seam, each in
its own worktree with a check-in log. Six had reported when these were
written, and between them they found THREE defects in the feature this
release is built around. None was in the code the previous fix had
touched; all three had shipped in the branch for a day.

**ROW 7 — A LIMIT PAINTED THE ELEMENT FLAT.** Setting a floor or a
ceiling rebuilds the ladder through `set_class_bounds`, which builds
every class with a placeholder grey, and the recolour below it is the
only thing that ever gives those classes their ramp colours. Its gate
asked about the ramp display window and about pins, never about
limits, so with a limit and the window left alone nothing recoloured
and the WHOLE ELEMENT drew `#c0c0c0` -- which on a map of areas reads
as no data. Measured through the dialog on a floor of -1000 over a
column of small positives, a limit excluding nothing whatever: five
Reds classes became five identical greys. The same commit had already
added `limits` to the ramp-span trim thirty lines below, so the value
reached the inner clause and not the gate standing in front of it.

**ROW 8 — A MOVED LIMIT NEVER RE-SPLIT.** Found by THREE hunts
independently, by three different routes, one of them in rendered
pixels. A limit is a geometry change, and the geometry signature
carried the split as `var if _needs_a_no_data_split(a) else None` --
a yes/no. Raising a floor from 20 to 40 answered yes both times, the
signature never moved, `_restyle_only` took the change, and it can
neither make nor unmake a split: the areas the higher floor newly
excluded stayed on the element layer with no class to place them and
drew as holes, while the notice said to press Generate, which changed
nothing. On a column already holding a null the predicate was true
before any limit existed, so even the FIRST limit was invisible.

IT IS THE SAME LESSON AS THE COMMENT DIRECTLY ABOVE THAT LINE, which
records the boolean-per-element fault of 2026-08-16 and ends "a
boolean summarising a field cannot see the field move". Widening the
predicate to know about limits put the limits behind that same
boolean. When you teach a PREDICATE about a new value, look at every
signature that quotes the predicate.

**ROW 9 — AN ADOPTED LADDER WAS NEVER STAMPED.** Nothing on a renderer
records that a break was CHOSEN rather than computed, so
`weavingspace_quant_style` is all a reopened project has. The four
colour adoption exits stamp and embed; the bounds exit was written
without either, so a ladder retyped in QGIS came back looking right
and the next Generate quietly recomputed the plugin's own numbers.
Found by two hunts, one of them reading the saved `.qgz` with
`zipfile` and the exported GeoPackage with `sqlite3` -- no QGIS in the
process at all.

AND TODAY'S EARLIER FIX MADE IT WORSE BEFORE IT WAS FOUND, which is
the part worth keeping. Recording `_last_signatures` there is what
stops the landing clobbering the ladder, and it also makes
`_restyle_only` skip the element -- so it silenced the only path that
had ever written the stamp late. The hunt put it exactly: when a fix
adds ONE line of an idiom, diff the WHOLE idiom. The siblings carried
four lines and the repair copied one.

## Rows 10 and 11 — the second round, and a control that never worked

**ROW 10 — EQUAL INTERVALS IGNORED A LIMIT.** The same shape as row 7,
in the same function: `cuts_from_the_pin` asked for a pin alone, while
the span chain inside the branch it guards already read "PIN, THEN
LIMIT, THEN DATA" and explained that a floor belongs there because the
rule exists so two columns given the same limits draw the SAME LADDER.
The value reached the inner clause and not the gate in front of it.
Measured through the dialog at five classes over 0-12: one element
drew 0-1-2-3-4-12 and the other 0-2.4-4.8-7.2-9.6-12, neither
equal-width and the two disagreeing everywhere between ends their
legends agree on. The flag is `cuts_from_the_ends` now.

MY FIRST MEASUREMENT OF IT PROVED NOTHING, and that is the part worth
keeping. It set the mode to "Quant: Equal interval", which is not a
mode -- the entry is plural -- so both elements stayed on Quantiles,
where two columns SHOULD disagree, and the run printed exactly what
the defect would print. Establish that a fixture's premise is true
before believing its conclusion.

**ROW 11 — THE CLEARING CROSS HAD NEVER BEEN CLICKABLE.** A
QDoubleSpinBox is a composite: Qt puts a QLineEdit inside it, and on
every platform measured that child starts at x=1 to x=3 and covers the
whole of the cross. So a real press went to the child and dropped a
text cursor into the number, and `mousePressEvent` on the box -- which
looks exactly like the handler -- was never called for those pixels.
Measured here at (3, 3, 96, 20) over a cross at (5, 8, 10, 10), with
`childAt` the cross's own centre answering QLineEdit.

THE GUARD PASSED THROUGHOUT because it handed the event straight to
the box with `QApplication.sendEvent`, which proves the HANDLER works
and not that anybody can reach it. It dispatches through
`QTest.mouseClick` now, so Qt picks the receiver. A test that
dispatches past the widget that would have received the event is a
test of a route no user takes -- and the fix is an event filter on the
line edit, since the child goes on covering those pixels whatever else
is done.

## Row 12 — the gate that tells and the gate that acts

The morning's own fix made this one. Once the geometry signature
carries the floor and the ceiling as VALUES, `_restyle_only` refuses
EVERY limit edit, so with live update off the map does not move until
the next Generate. The notice beside it went on asking the narrower
question it was written for -- do the limits currently exclude
anything -- so a floor set wide of the data, or lowered, or given
back, changed nothing and announced nothing. That reads exactly like
the control not working, which is the harm the notice exists to
prevent.

TWO SENTENCES, because one cannot be honest about both directions.
Setting a limit that excludes stops areas being drawn; widening or
clearing one starts them again.

AND IT EXPOSED A VACUOUS GUARD OF THE SAME MORNING.
`test_a_limit_keeps_the_colours_the_ramp_gives` drove

is not deferring, so nothing here is exercised" — fired by a test
whose own subject is something else entirely. The repair had been
proved against row 19's own guard and against nothing that picks a
style FIRST. The lesson is the one this project keeps paying for from
new directions: A GUARD THAT ASKS ABOUT ONE THING MUST NOT STAND IN
FRONT OF AN EXIT THAT IS ABOUT ANOTHER, and the tell here was reaching
for a flag that already existed rather than recording the fact the
guard actually needed.

Guarded by `test_a_style_picked_by_hand_still_follows_a_paste_in_qgis`,
which drives the paste AND the Generate after it AND the reclaim that

catalogue entries: the reader, the writer and the dock's discard,
anchored separately because the trio is enforced by nothing but

## Row 25, closed: the tenth candidate was named the ninth

`release.py --rc` built `weavingspace_qgis-0.24.3rc10.zip` from a tree
that had passed every gate, and then wrote that candidate's dossier
and receipt as **rc9** — on top of the published rc9's own, which
described a different commit. One name over two trees, which is
exactly what the candidate numbering exists to prevent, arriving from
the end nobody was watching.

TWO FAULTS IN ONE LINE, and neither could show itself before today.
The candidate was named by sorting `dist/weavingspace_qgis-*rc*.zip`
and taking the last entry. In TEXT order `rc10` sits between `rc1` and
`rc2`, so `rc9` came last — and this is the tenth candidate of 0.24.3,
the first two-digit candidate this project has ever built. The glob
was not scoped to the version either, so a 0.25.0rc1 would have been
named from a leftover 0.24.3 candidate.

`next_candidate` was RIGHT the whole time and is why the zip is
correct: it parses the number and takes `max() + 1`. The naming was a
SECOND derivation of the same fact, written in a different file by a
different route, and a rule with two implementations has two
behaviours the day one of them is wrong. It is `build.latest_candidate`
now, beside `next_candidate` and sharing its notion of what an
artefact is; `release.candidate_just_built` is three lines that ask it.

THE GUARD COMPUTES THE OLD ANSWER AND REQUIRES IT TO DISAGREE, because
nine candidates satisfy both derivations and the fixture had to reach
ten to mean anything.
`test_the_tenth_candidate_is_named_the_tenth`.

IT FAILED FIRST ON A FALSE PREMISE OF ITS OWN, which is the smaller
lesson and a real one: it patched `DIST` on its own copy of build.py
while `release.build_module()` re-executed the file per call and
answered from another. A rule with several live copies is a rule
nobody can ask a question of, so the module is loaded once now and the
test steers the object production uses. The reflex to fix the product
and the reflex to fix the test are equally strong and both were wrong;
what was mistaken was the seam between them.

WHAT WAS DONE ABOUT THE ARTEFACTS is in `dist/WHAT-HAPPENED-2026-08-19.md`,
beside the files, because `dist/` is gitignored and a note in a commit
would not be where anybody meets them. rc10's dossier and receipt were
written under its own name against the digest the gates measured — the
maintainer's call, rather than spending a number on a rebuild that
would measure byte-identical shipped files. rc9's were RECONSTRUCTED
from its tag and say so: the zip is byte-identical to the published
one, the dossier came from running rc9's own tool inside a worktree at
`v0.24.3rc9`, and the receipt carries a digest recomputed the same
way. What no tree can reproduce — the moment its gates passed — is
declared missing rather than invented.

## Rows 26, 29 and 31, closed: a mark nobody could see, and what it cost

THE CROSS THAT GIVES A BOUND BACK HAD NEVER BEEN VISIBLE ON ANY BUILD.
`MarkableSpinBox` painted it five pixels from its own left edge, which
is inside the QLineEdit a QDoubleSpinBox puts there, and Qt paints a
child AFTER its parent. Measured on a marked box grabbed offscreen:
721 dark pixels for the heavy outline and ZERO inside the cross's own
rectangle.

THE CLICK HAD BEEN REPAIRED THE MORNING BEFORE and the paint left
underneath it. `_keep_the_text_clear`'s own docstring says "the line
edit goes on covering these pixels whatever its margins say" -- the
sentence was written by whoever fixed the click, and not followed to
the paint. THE FIX TOOK THE HALF THAT HAD BEEN REPORTED.

WHY THE GUARD PASSED THROUGHOUT: it drove the click and counted dark
pixels over the WHOLE widget, which the heavy outline alone satisfies.
It never looked inside the cross's own rectangle. Two later attempts
to close that gap were caught by the catalogue in turn -- the first
hid and re-showed the mark to get a contrast, which CALLS `show()` and
`raise_()` and repaired the mutation on its way past; the second ran
after the test had given every bound back, so no box was marked and
the block never executed. A guard that mends the defect, and a guard
with nothing to look at, both read exactly like a guard that works.

ROW 29 WAS THE SAME DEFECT WEARING ITS CONSEQUENCE. With all four ends
set by hand there is nothing on screen saying what the computed value
WAS, so the cross is the only practical way back -- and it could not
be seen. Measured after the repair, with all four set: the cross
releases one, retyping the computed value releases another, and the
other two stand.

ROW 31 IS THE SAME SHAPE IN THE SWATCH. Its marks were built from
`low` and `high` while the record had held four ends since that
morning, so a floor or a ceiling drew nothing. FOUR ENDS ON FOUR
EDGES, on the maintainer's design: the first class's left edge is the
floor and its right edge the low pin, the last class's left edge the
high pin and its right edge the ceiling. It says WHICH bound is yours
rather than only that something in that class is, and it composes.
Sixteen combinations rendered and counted; the inset went from 1.5 to
2.5 because the ceiling's white stroke on the icon's outer edge
vanished into the page behind it. A mark nobody can see is a flag,
twice in one evening.

## The harms, written before any code was read

Each of 0.24.3's changes, asked "what does this let the software take
from somebody who has spent an afternoon on a map?"

1. The paired NO-DATA LAYER is a second QGIS layer with no dialog row
   of its own. Anything a user does to it in QGIS — colour, hatch,
   filter, opacity — has no record in the plugin, so it is the
   likeliest thing on the map to be silently rebuilt. (The opacity
   half of exactly this was fixed the day the feature shipped, which
   says the harm is real and says nothing about the other halves.)
2. The no-data COLOUR itself, picked in the editor, lost at a reopen
   or a landing — the rule that has now bitten three times.
3. A pinned bound or a copied ladder destroyed by an ordinary action.
   Six hunts and eleven defects have been here; deprioritised.
4. Breaks cut from the wrong pool: the whole-map values cached against
   a stale key.
5. The categorical Classes count read from a stale cache.
6. A scale factor of zero reachable, or a typed 0.5 mangled by the
   step-over-zero guard.
7. The fast legibility check answering differently from the slow one.

Started at 1, on the reasoning that a second layer nothing in the
dialog names is where a promise made to the first one gets forgotten.

## Harms ruled out, or not reached

- **Harm 2 (the no-data colour lost at a reopen).** RESULT: ruled out
  by reading. `_quant_colours[tile][field][NO_DATA_KEY]` rides in the
  same `weavingspace_quant_style` stamp as the positional class picks
  (dialog.py:3776-3801) and comes back through `_adopt_category_colours`
  (3868-3884); `_add_no_data_layer` reads `self._quant_colours` live
  at the landing (6386), not the launch snapshot, which is what the
  three previous instances of that rule required.
- **Harm 3 (pins and copy).** Not pursued: six hunts, eleven findings,
  and the settled decisions cover the two behaviours that look wrong.
- **Harm 4 (breaks from a stale pool).** RESULT: ruled out by reading.
  `_classification_values` keys its cache on
  (layer id, field, fingerprint, `_data_version`) (dialog.py:2802) and
  replaces rather than adds; the documented provider-level limit is
  the only gap and is a stated limit.
- **Harm 5 (stale categorical count).** RESULT: inconclusive, low
  harm. `_cat_count_cache` is keyed on (layer id, field) alone with no
  fingerprint (dialog.py:2739), so an edit that adds a value can leave
  it stale — but the element's OWN drawn layer is asked first once a
  map exists, and the cell is a report rather than anything the map is
  drawn from. Not worth a maintainer's afternoon.
- **Harm 6 (scale factors).** Not probed. `_skip_zero_scale`
  (dialog.py:1862) is connected to `valueChanged` with keyboard
  tracking left on, so typing a value that passes through "0" ought to
  be mangled into ±0.02; that is a control fighting the user in
  plain sight rather than a loss they would not notice, and it needs
  QTest key events to drive honestly. Worth someone's next hour.
- **Harm 7 (the fast legibility check).** Not reached; the perf hunt
  of 2026-08-16 has been over that ground.

## The finding, in the form the brief asks for

**The harm.** A user who styles an element's "no data" layer in QGIS's
Layer Styling panel — a distinct colour, a hatch, a filter — loses
that work at the next Generate, while the identical hand styling on
the element beside it survives and is announced; nothing tells them,
and there is nothing to undo.

**Reproduction.**
`python3 tools/hunt_probe.py --name harm-0243 --run p_paired_vs_element.py`
(probe listed above): generate a map on a column with a NULL, recolour
both `a – v1` and `a – no data` to #ff00ff in the styling panel and
give both a filter, change the spacing, Generate.

**Measurement.** element (#ff00ff, filter kept) against no data
(#dddddd, filter dropped); in the GeoPackage's own `layer_styles`,
`tiles_a` carries 255,0,255 and `tiles_a_no_data` carries 221,221,221.
Second door: a style-only change destroys it in place with no re-tile.

**Where it goes wrong.** `dialog.py:7792-7815` collects
`old_renderers`, `old_layer_opacity` and `old_subsets` for the element
and only `old_no_data_opacity` for its twin; `dialog.py:6386-6390`
(`_add_no_data_layer`) and `dialog.py:6285` (`_restyle_no_data_layer`)
then overwrite the paired renderer unconditionally.

**When it started.** dd112bf, the commit that added the feature.

**Confidence.** High on the measurement, and it is the shape this
project keeps meeting: a fix applied to one attribute of a new object
and not to its siblings. What would change my mind is a maintainer's
ruling that the paired layer's appearance belongs to the plugin
outright — though the opacity carried across at 920369c, the subset
string carried for the element on the same stated promise, and the
notice raised for the element's dock recolour all point the other way.

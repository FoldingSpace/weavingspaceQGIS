### 1. The cancel that was cleared under the writer

**The mechanism, and why it could not be seen by reading the line.**
`write_gpkg_layers` asks `should_stop` between tables and answers True
with a rollback, so the flag is the whole of the mechanism. The hold
that offers the button cleared that flag on its way out, under a
comment giving its reason: "a write that DID read it has already
returned by the time this line runs -- the pump that delivered the
click sits inside that write". That is TRUE of the ordinary deferred
press and FALSE when the close or the quit is delivered BY THE WRITE'S
OWN PUMP, which turns the event loop once per element behind its
progress bar. The hold then runs in a frame NESTED BELOW the writer,
so the clearing happened while the writer was still suspended above
it.

**Measured at the seam rather than deduced.**
`tools/probes/what_a_cancel_during_the_write_does.py` drives three
arms in one process and wraps the `should_stop` argument the dialog
hands the real writer, so what is recorded is what the PRODUCT was
told:

    CONTROL   nothing interrupts     four tables, "Saved to control.gpkg."
    WRITING   cancel while writing   four tables, "Saved to writing.gpkg.",
                                     should_stop asked 4 times, told
                                     [False, False, False, False]

    after the repair                 no tables, "The save was stopped,
                                     so the map was not written.",
                                     should_stop told [True]

**Two doors, two readers.** The hunt drove QGIS's QUIT through the
event filter and read the file with stdlib sqlite3; the verification
drove the PLUGIN WINDOW's own close, which reaches the same hold from
`closeEvent` after its question is answered Save, and read the file
through OGR.

**The repair is one condition**, and the reason is written at the
line: the clearing runs only where no write is in progress. A write
already under way is left to its own branch, which clears the flag,
rolls the transaction back and says the map was not written. Both
directions are asserted in the guard, because the obvious repair --
never clearing -- passes everything except the person's NEXT save,
which is the fault this same flag caused on 2026-09-01.

### 11. The filter that was written as though it were the map

`write_gpkg_layers` iterates `getFeatures()`, which honours a layer's
subset string. So a filter -- a thing a person sets to LOOK at part of
their map -- was written into the file as the map itself.

TWO ROUTES REACH IT AND ONLY ONE INVOLVES THE SKIP. A layer already
reading from its own table is treated as saved already, and identity
was `same_source` over the WHOLE tail of a source string, which a
subset lives in; so a filtered layer failed to match the table it was
plainly reading from and went down the write path into that table. But
a RE-TILE gives every element a new memory layer and carries the
person's filter onto it deliberately, and no skip can fire there at
all -- which is the route the hunt did not drive and the worse of the
two.

MEASURED ON THREE ARMS IN ONE RUN
(`tools/probes/what_a_filter_does_to_a_save.py`):

    control   two saves, no filter          41/40/41/40 unchanged
    second    filter between two saves      tiles_a_v1  41 -> 3
    re-tiled  filter, then design changed   tiles_a_v1  41 -> 0

The zero is the sharp one: the filter names feature ids that the new
tiling never produced, so it selects nothing and the element's table
is emptied.

### 1. The cancel that was cleared under the writer

**The mechanism, and why it could not be seen by reading the line.**
`write_gpkg_layers` asks `should_stop` between tables and answers True
with a rollback, so the flag is the whole of the mechanism. The hold
that offers the button cleared that flag on its way out, under a
comment giving its reason: "a write that DID read it has already
returned by the time this line runs -- the pump that delivered the
click sits inside that write". That is TRUE of the ordinary deferred
press and FALSE when the close or the quit is delivered BY THE WRITE'S
OWN PUMP, which turns the event loop once per element behind its
progress bar. The hold then runs in a frame NESTED BELOW the writer,
so the clearing happened while the writer was still suspended above
it.

**Measured at the seam rather than deduced.**
`tools/probes/what_a_cancel_during_the_write_does.py` drives three
arms in one process and wraps the `should_stop` argument the dialog
hands the real writer, so what is recorded is what the PRODUCT was
told:

    CONTROL   nothing interrupts     four tables, "Saved to control.gpkg."
    WRITING   cancel while writing   four tables, "Saved to writing.gpkg.",
                                     should_stop asked 4 times, told
                                     [False, False, False, False]

    after the repair                 no tables, "The save was stopped,
                                     so the map was not written.",
                                     should_stop told [True]

**Two doors, two readers.** The hunt drove QGIS's QUIT through the
event filter and read the file with stdlib sqlite3; the verification
drove the PLUGIN WINDOW's own close, which reaches the same hold from
`closeEvent` after its question is answered Save, and read the file
through OGR.

**The repair is one condition**, and the reason is written at the
line: the clearing runs only where no write is in progress. A write
already under way is left to its own branch, which clears the flag,
rolls the transaction back and says the map was not written. Both
directions are asserted in the guard, because the obvious repair --
never clearing -- passes everything except the person's NEXT save,
which is the fault this same flag caused on 2026-09-01.

### 2. The handle the table did not grow for

`_drag_moved` answers one question -- did this gesture ask for
anything -- and it answers it PER MANIPULATION, because each has its
own idea of nothing: zero travel for a nudge, half a degree for a
rotation, one per cent for a scale. It was written on 2026-08-30, when
a vertex carried ONE handle. The push rail arrived the next day with
the ruling that every manipulation is reachable on the drawing, and
the fall-through answered False for it.

MEASURED THROUGH THE WIDGET'S OWN MOUSE EVENTS
(`tools/probes/does_a_push_drag_reach_the_record.py`), with the nudge
handle on the same vertex as the control:

    push_vertex   previewed, asked for push_d=0.153, record 0 -> 0
    nudge_vertex  previewed, asked for dx=0.105,     record 0 -> 1

    after the repair, push_vertex                    record 0 -> 1

THE GUARD IS THE SHAPE RATHER THAN THE INSTANCE. Every key in the two
handle tables is put to `_drag_moved` with a gesture past every
threshold and must be answered yes, so the SIXTH handle is covered by
whoever adds it; and the push is then driven end to end through the
widget, because a table answering correctly is not a gesture reaching
the record.

### 3. The repair's own defect, found within the hour

Row 1's repair narrowed the hold's clearing to "where no write is
running", which is right for the moment it was written for and leaves
a later one uncovered. The writer clears the flag only where IT read
one, between tables; the hold now leaves it alone while a write runs;
and a cancel landing AFTER the last table -- during the repointing or
the styling, 13.0s of a 256-element save -- falls between the two. The
flag then stands for ever and the next save is rolled back.

IT WAS FOUND BY A HUNT AIMED AT THE ROUND'S OWN REPAIRS, which is now
TEN ROUNDS FOR TEN in this project's record, and the repair it read
was ninety minutes old. The flag is cleared where the act ENDS now,
in the same `finally` as `_saving_now`.

AND ITS FIRST GUARD SURVIVED THE MUTATION, which is what sent the
entry to a second test: row 1's guard cancels BETWEEN tables, where
the writer's own branch clears the flag, so removing the line changed
nothing it could see. The journey has to reach the moment, and the
moment is staged by wrapping the seam -- a wrapper that calls the real
writer and then asks for the close -- rather than by timing a click.

### 4. A file that holds nothing is nobody's

The ownership question is asked once per press and CACHED for the
session, and it decided by `os.path.getsize(path) > 0`. A GeoPackage
OGR has created and nothing has written to is 65,536 bytes of header
holding no layer -- non-empty by size, empty by content -- and
`_this_map_owns_the_file`'s own docstring says an empty file "is
nobody's and is decided by the caller". Measured with a control: after
a cancelled first save, shrinking a four-element design to two left
`tiles_c_v3` and `tiles_d_v1` in the file where the same journey
without the cancel dropped them. It asks `bridge.gpkg_tables` now, and
the guard asserts BOTH directions, since a repair that made every file
ours would destroy a colleague's work.

### 5. A save that outran its own build

`_a_topology_is_owed` asks THE FILE, which is the cost ruling of
2026-08-30 and is right about whether to START a build: somebody who
has never opened the Topology tab pays none of it. It was the wrong
question about a build ALREADY RUNNING. Measured, both arms in one
run: hurried, no motif and `topology_written: False`; after a pause,
`weavingspace_unit_no_crs` and its dual. The press waits for work
already under way now, and the guard asserts the cost ruling beside
it, because the obvious repair overturns it.

### 6. A wait only an outer frame could end

`_save_the_map` turns the event loop once per element, so a close or a
quit arriving during a write is delivered by THAT WRITE'S OWN PUMP and
the hold runs nested inside it -- spinning until `_saving_now` clears,
which only the suspended frame beneath can do. Measured through both
doors with the ceiling shortened and said so: 5.1s against a control's
0.16s, and no tables at all once the escape pressed Cancel. The hold
declines where a write is already running: the save lands the moment
it returns, so the act is let through and the map is written.

AND IT PUT TWO OF THE DAY'S OWN ENTRIES TO SLEEP, which is this
project's recorded shape and is recorded again here. With the hold
unable to run beneath a writer, both of rows 1 and 3's conditions
became redundant -- the hold's branch now always executes after the
act has ended. Both entries are RETIRED with their measurements at the
catalogue, both lines KEPT as defence in depth, and what would reopen
each is written where it stood. The OUTCOMES are still guarded: a
cancel during a write rolls back, and a late one does not poison the
next save.

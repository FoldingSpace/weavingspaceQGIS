## Defect 1, and why three hunts found the same thing

Aimed at different shapes -- asymmetry between two doors, the journey
of a recolour across boundaries, and two new stores -- all three
arrived at one line. That convergence is itself evidence: the same
defect reached by three routes is not an artefact of one probe.

The repair for ledger row 28, written the day before, added a second
door into the style handler and a guard on it: skip an element whose
row has moved, because between a control change and the restyle that
answers it the layer is merely BEHIND, and reconciling then adopts the
plugin's own outgoing style as somebody's picks. That guard is right.
What was wrong is how it asked:

    if self._signature(assignment) != self._last_signatures.get(tile_id)

`_adopt_existing_group` leaves `_last_signatures` EMPTY, deliberately,
and says so in its own docstring: the dialog cannot know which
assignments produced layers it has only just met. So `.get()` answered
None for every adopted element, None never equals a real signature,
and every element of every reopened project took the skip. The door
was shut in exactly the session whose docstring promises that "hand
styling still survives as before".

VERIFIED BY THE GUARD'S INPUTS rather than by rendered colours:
`_last_signatures` holds 4 entries in a fresh session and 0 after a
reopen, and the dump reads `REPAINT a queued` then `REPAINT a
row-moved`. A hunt confirmed it a fourth way, reading the QML out of
the GeoPackage with sqlite3 and no QGIS involved.

**THE LESSON: ABSENT IS NOT MOVED.** When a new guard reads an OLD
record, ask which paths leave that record deliberately empty. A
missing entry is the absence of evidence, and reading it as evidence
of change inverts the guard exactly where the record is emptiest.

## Defect 2, one repair attempted and withdrawn

`count_moved` was written on 2026-08-19 to stop a class ADDED in QGIS
having its shuffled colours adopted. It works on the signal that
carries the change and on no signal after it: the flag is a delta
across `_row_follows_the_renderer`, and the follow has already brought
the row up to date, so the second pass finds nothing moved.

Measured, driving the dialog and reading both the record and the
stamped property: a hand-picked `#ff00ff` on class 2 survives the
class being added, and one bare repaint later the record holds four
colours with the magenta displaced to class 3.

THE FIRST ATTEMPT AT A DURABLE VERSION WAS WITHDRAWN THE SAME HOUR.
It replaced the delta with the right question -- is this the ladder
the row would draw? -- by comparing BOUNDS rather than counts. That is
correct in the reported case and over-reaches everywhere else: once a
class has been added in the dock the ladder differs from ours
permanently, so no hand-pick would ever be adopted for that element
again. Reverted, and recorded here so the next attempt does not repeat
its shape.

WHAT THE NEXT ATTEMPT MUST SETTLE FIRST, because it is a decision
rather than a defect: after somebody reclassifies an element in QGIS's
own panel, WHOSE LADDER IS IT? If it is theirs, the element should
DEFER and positional adoption should stop entirely. If it stays ours,
adoption needs the ladder we drew STORED rather than derived, since
deriving it is what both attempts got wrong.

## How that decision went, and what the store turned out to be

Settled by `/grill-me` on 2026-08-20, and the FIRST question was
whether the ledger had framed it fairly. It had not. The "theirs, so
it defers" limb is not a peer of the other: deferral in this plugin is
INFERRED afresh every time from `bridge.expressible_style`, never
stored, on a maintainer's condition of 2026-08-15 -- and a six-class
graduated ladder is perfectly expressible, so nothing about a
reclassification makes it defer. Taking that limb would have meant
overturning that rule AND the follow ruling of 2026-08-17, which had
already considered and rejected deferring on any outside edit.

So the question narrowed to the one that was actually open: not whose
LADDER it is, but which COLOURS on it the plugin put there. The
maintainer chose the narrow reading, and the rest followed from one
measurement.

**`addClass` KEEPS EVERY SURVIVOR'S BOUNDS BIT FOR BIT.** Measured on
QGIS 4.0.3: the green + hands the source symbol to `addClass`, which
inserts a DEGENERATE `(0.0, 0.0)` class at index 0 wearing the
placeholder grey, and the five survivors keep their ranges exactly.
So a colour CAN be matched back to the class it was painted on, with
no tolerance at all -- which is what makes a store answerable where a
derivation is not.

`_painted_ladders` holds `[(lower, upper, colour)]` per element and
field, written wherever the plugin paints and at group adoption, and
NOT stamped: a reopened project re-derives its baseline from the layer
in front of it, which keeps the record out of the restore whitelist
this project has been bitten by twice.

AND THE FIRST DRAFT OF THE JUDGEMENT HAD ITS OWN DEFECT, which is
ledger row 7 and the more useful half of this entry. `_colour_is_ours`
looked up a class by its bounds and RETURNED ON THE FIRST MATCH. A
ladder may hold several classes with identical bounds -- a constant
column, a tied column, `{1, 5, 9}` at k=5 -- and the inserted
`(0.0, 0.0)` class collides with any fixture whose first real class is
also degenerate. So the plugin's own `#fff5f0` was compared against
the grey sharing its bounds, judged changed, and adopted. FOUR TESTS
PASSED THROUGHOUT. What found it was driving the product and printing
the store at each stage, which is this project's own prescription and
was still not the first thing tried.

## Defect 4, and a site named by reading rather than by measuring

The fingerprint half was fixed first and did not cure it: a ramp
picked after the file moved still did not reach the map. What the
handover, this ledger, ROADMAP.md, MAINTAINING.md and docs/TESTING.md
all then said was that `_generate`'s availability check stands in
front of its restyle fast path and refuses silently on a live run.

That was wrong twice, and one probe settled both in a single run. A
live tick never reaches `_generate` at all: `_maybe_live_generate`
holds ten gates of its own, and the sixth is the same availability
question. And the refusal is not SILENT -- it says "That layer's data
is no longer available, so the map cannot be updated", which is a
false sentence, because the map could have been repainted. A wrong
explanation is worse than none: it sends the reader to their data.

    LIVE-GATE source-gone                     <- the actual refusal
    LIVE-GATE restyled-without-the-source     <- after the fix

**THE LESSON IS ABOUT WHERE A LOCATION COMES FROM.** The site was
read out of the source and written down as fact, and by the time it
was measured it had propagated into four binding documents in one
documentation round -- which is exactly the cost this project already
records for a rule that asserts its own enforcement. Every gate on
that path now NAMES ITSELF behind `WEAVINGSPACE_ADOPT_DUMP`; live
update pausing without saying why has now cost two diagnoses, this one
and ledger row 3's icon-mode estimate.

THE TWIN WAS CHECKED RATHER THAN REPAIRED. `_generate` puts its
restyle fast path ABOVE its own availability check, so a button press
was never blocked, and giving it the same repair would have been dead
code reading as protection -- the pairs rule cutting the other way.
The test's second act drives that door, and a catalogue entry reverses
the order to prove the act can fail.

AND THE FIRST MUTATION WRITTEN FOR IT SURVIVED, correctly:
`self._restyle_only() and False` evaluates left to right, so the
restyle still ran and still repainted, and only the `return` was
skipped. A mutation whose side effect survives it breaks nothing a
test can see. Short-circuit ahead of the call.

## Defect 5, the oldest of the round, and why the drop was defensible

Ten days old, and the line that caused it was not careless.
`dock_colours` dropped `NO_DATA_KEY` because the TRIAL renderer is
built from the ramp alone, and a ramp has no opinion about the
catch-all: comparing the layer's catch-all against the plugin's
default would have made every element with an edited catch-all fail to
follow a ramp it really was following.

The repair is to ask a different question rather than to stop asking.
The catch-all is compared against `expected` -- what THIS ELEMENT
draws right now, default or earlier pick alike -- and not against the
trial. A clean Classify leaves that class alone, so the follow branch
loses nothing; a recolour moves it, which is precisely the difference
the two branches exist to tell apart. Unknown on either side does not
block the follow, because absence of evidence is not evidence of a
pick -- the mistake made in the other direction on the 19th.

THE TEST PROVES ITS OWN CHANNEL BEFORE ASSERTING SILENCE ON IT. The
fixture builds its dialog with `iface=None`, where `_report_quietly`
writes to the note line and never to the message bar, so reading
`BAR_MESSAGES` alone would have been an assertion that could not fail.
It now raises a notice by hand, asserts that it appears where the test
reads, clears it, and only then requires the wrong sentence to be
absent.

AND THE FREED-TEMPORARY TRAP TOOK ME A FOURTH TIME, four lines under
my own comment warning about the copies half of the same getter:
`edited.categories()[index].symbol()` took QGIS down with no output,
which the runner reported as exit 0 because the verdict was piped into
`tail`. Two rules, both already written here: bind the list before
subscripting it, and never let a pipe stand between a gate and its
status.

## Defect 6, and a promise that was being kept by an echo

The repair is one line of judgement: the guard demanded that NO colour
had moved, which is right about a Classify -- it picks a ramp and
rewrites every class -- and wrong about the visit where somebody
retypes a boundary AND recolours a class. A WHOLESALE repaint is a
Classify; a PARTIAL one is somebody's hand. What it still refuses is
unchanged, and the cost is stated at the site: recolouring every class
one at a time in a single visit reads as a Classify.

**THE INTERESTING PART IS THAT IT NO LONGER REPRODUCED.** Written as
the ledger described it, the guard PASSED against the unfixed code.
The gate dumps said why in one run: the first signal declined with
`colours-moved`, and a SECOND signal -- echoed by the colour
adoption's own stamping, synchronously, inside the same `emit()` --
adopted the bounds a moment later. The record came out right by an
accident of ordering, which is the very shape this row exists to name,
arriving in the repair rather than in the bug. A promise kept by an
echo is not kept.

**AND THE CATALOGUE PROVED THE TEST COULD NOT SEE IT.** The first
entry SURVIVED: with the echo doing the work, breaking the fix changed
nothing the test asked about. What made it visible was a second arm
staged so that no echo exists -- a colour MOVED from one class to
another, which `_colour_is_ours` declines, so nothing is adopted,
nothing stamps, and no second signal follows. Whatever that visit
records is all there is. The entry is caught on that arm.

THE TRANSFERABLE RULE: when a defect stops reproducing, ask what is
now doing the work rather than whether it is dead -- and if the answer
is a second pass, the guard must be staged where the second pass
cannot happen.

## What the round ruled OUT, so nobody spends the time again

Worth as much as the findings, and cheaper to lose:

- a merely EMPTY layer: `featureCount()` is 0, the probe is skipped,
  the answer is True, and no caller changes branch;
- a `featureCount()` of -1 (WFS, PostGIS, an ArcGIS service): also
  skipped, also True, unchanged;
- a subset string matching nothing on a clean GeoPackage: the count is
  subset-aware, so 0, so skipped, so True;
- the availability probe's cost on an UNFILTERED layer: 0.12 ms and
  flat to 50,000 features;
- all nine `_dump("DROP")` branches are reachable, `field-mismatch`
  included -- retype the Value field to a column the output layer
  carries and the variable combo does not offer. One CLAUSE is dead,
  `assignment["mode"] != "Graduated"`, because the follow runs first
  and the mode list holds every `Quant:` label. Nobody loses anything;
- `_style_signal_at` is cleared by no site at all, and the staleness is
  INERT: the clock is monotonic and the window one second, so a stale
  key does nothing.

## Defect 9, and the two tests that were guarding nothing

The ledger closed at eight rows, and the handover named three holes
rather than counting them. Two were tests with no catalogue entry --
the dataset-switch pair, written that afternoon against ground
recorded as ALREADY SOUND. Writing the entries they owed is what found
this.

**BOTH TESTS WERE VACUOUS, AND FOR ONE REASON.** Their fixture
assigned a variable and never touched the STYLE chooser.
`_refresh_table` restores a style only where somebody chose it and
otherwise RE-DERIVES one from the column's type, so on every switch
the plugin recomputed a quantitative style for the new numeric column.
Nothing was retained, so nothing could be wrongly retained, and the
interesting assertion in each sat behind an `if` that was false. Both
green results said only that something had happened.

**MEASURED WITH THE STYLE PICKED THROUGH THE COMBO** -- `activated`,
which is what a click sends and what marks the choice as the user's --
a categorical scheme cut for four land-cover words came to rest on
`density` and on a `landcover` that had become thirty-six floats, in
both cases drawing a colour for each. That is the colleague's report,
live while CLAUDE.md, ROADMAP.md and the handover all said the ground
had been measured sound.

**THE THIRD DOOR CAME OUT OF A SURVIVOR.** The entry aimed at the
restore branch would not die, because the rule is written at two
places in `_refresh_table` and a change of dataset rebuilds the table
TWICE -- so either half answers alone and neither can be killed.
Asking why is what turned up `_adapt_to_the_layer`, which re-points a
row at a surviving column BEFORE the rebuild, so the guard there
cannot see the case at all. Deleting `landcover` in QGIS moved the
element to a numeric `v2`, told the user so, and left the categorical
scheme standing. One implementation, one line, and an entry that
catches.

**THE CATCH-ALL SURVIVAL AXIS IS REDUNDANT RATHER THAN DEAD**, and
that was measured too: the landing CARRIES the old renderer where an
element's assignment has not changed, and rebuilds from the record
where it does not. Mutated one at a time the test passes; broken
together it fails at once, naming the grey. Recorded at the test
instead of as an entry that could only ever be red.

**AND TWO SMALLER THINGS FELL OUT OF THE SAME READING.** The
categorical copy wrote its class source into the receiving row's
column-7 cell -- which EXISTS ONLY ON A CATEGORIZED ROW, so copying
onto a quantitative element wrote it into nothing and the two elements
disagreed while the window said they matched. And the copy's note
about kept colours was slotted into a frame built for noun phrases, so
every copy that lost a value read "Element 'b' gave up kept 5 colours
for values 'code' does not have."
